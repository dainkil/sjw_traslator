# 실측 벤치마크

모든 수치는 실측이며, 측정 방법·환경을 함께 기록한다. (계획서 원칙 4)

## NER: ONNX 변환 전후 비교 (M1, 2026-08-31)

- 환경: Apple M5, 16GB RAM, CPU 단건 추론 (배치 없음)
- 데이터: 골든셋 `eval/eval300_1925.json` 중 무작위 100문장 (seed=42)
- 재현: `cd ner-server && uv run python scripts/benchmark.py --n 100`

| 엔진 | mean | p50 | p95 | PyTorch 대비 엔티티 완전일치 | 골든셋 PER recall | 모델 크기 |
|---|---|---|---|---|---|---|
| PyTorch (기준) | 28.9ms | 17.9ms | 68.7ms | — | 102/102 (100%) | 709MB |
| ONNX fp32 | 16.1ms | 10.6ms | 65.4ms | 100/100 (100%) | 102/102 (100%) | 709MB |
| **ONNX INT8 (채택)** | **14.8ms** | **8.3ms** | **62.4ms** | 97/100 (97%) | **102/102 (100%)** | **178MB** |

**규칙 기반 축소판 대조 (M2.5-S3, 2026-09-01):** `RulePatternRecognizer`(정규식 3규칙: 以◯爲 제수 / 성씨+행위동사 / 관직+성명) — 동일 골든셋에서 **PER recall 26.9%, precision 62.0%** (tp=103 fp=63 fn=280, `RulePatternRecognizerTest` 회귀 하한 포함). ONNX recall 100%와의 이 격차가 "KB 주입 효과" A/B의 대조군이자 NER 장애 시 degrade 경로의 비용이다. 교체는 `NER_MODE=rule` 설정만으로 (수용 기준 2).

**해석**
- INT8 채택: p50 기준 2.2배 빠르고 메모리 4분의 1. 문장 단위 완전일치가 97%로 소폭 떨어지지만, 실제 파이프라인이 소비하는 신호(PER surface 검출)는 골든셋 recall 100%로 동일.
- 계획서 §2.1의 "NER 100~300ms (CPU)" 가정 대비 **한 자릿수 ms로 실측** — NER은 지연 예산에서 사실상 소거된다. GPU 배제(ADR-003)의 실측 근거가 이 표다.
- 주의: 서버 경유 시 HTTP 왕복이 추가된다. 파이프라인 관점 지연은 M1 완료 시 단계별 분해로 재측정.

## E2E 단계별 지연 분해 (M1, 2026-08-31)

- 경로: API(:8080) → NER 서버(:8100) → KB 링킹(in-memory) → 프롬프트 조립 → Gemini (무료 티어)
- 데이터: 골든셋 무작위 샘플 (seed=42), 순차 호출 + 6초 페이싱
- 재현: `uv run --with httpx python eval/measure_e2e.py --n 30 --pause 6`

**내부 단계 (모델 무관, 실측):** NER 19~24ms(HTTP 왕복 포함; 서버 내 추론은 8.3ms), KB 링킹 ≤1ms, 프롬프트 조립 ≤1ms.

**LLM 단계 (모델별 실측):**

| 모델 | n | llm mean | llm p50 | llm p95 | **LLM 비중 (p95)** | 토큰 in/out (평균) |
|---|---|---|---|---|---|---|
| gemini-3.5-flash (T1 기본, thinking) | 17 | 12,112ms | 11,959ms | 18,812ms | **99.9%** | 820 / 115 |
| gemini-3.1-flash-lite (T0 후보) | 10 | 3,237ms | 2,988ms | 6,475ms | **99.7%** | 822 / 130 |

> **§2.1 확정: 전체 p95의 99.7~99.9%가 통제 밖 외부 LLM이다.** 계획서의 "90% 이상" 가설이 상회 확정됐다.
> 내부 최적화(NER GPU 등)의 ROI가 0에 수렴한다는 D3 결정의 최종 근거.

**부수 관찰 (무료 티어 운영 현실, ADR-016):**
- `gemini-3.5-flash` 일일 무료 한도 **RPD 20 실측** (429 응답의 `quotaValue:"20"`, `PerDayPerProjectPerModel`). 30문장 측정 중 13건이 이 한도로 차단됨 → n=17.
- quota가 **모델별로 독립**이므로 티어 라우팅(M4)이 곧 일일 quota 풀링이 된다.
- `gemma-4-26b-a4b-it`는 혼잡 시간대에 짧은 프롬프트도 16초+, 전체 프롬프트는 60초 타임아웃 — 무료 엔드포인트의 시간대별 변동성이 크다. 배치 워크호스 선정은 M2에서 RPD·안정성 실측 후 결정.
- 요청당 입력 ~820tok = 페르소나 448 + Structured Output 지시문·KB블록 ~250 + 원문 ~120. 오버헤드 비중 85%.

동일 인물(領議政李元翼)을 포함해도 문장에 따라 전 토큰 O 예측이 나온다 (예: `...進曰臣以老病...勉留之` 45자 문장 — PyTorch 원본도 동일). silver-label 학습의 문맥 민감성으로, 서빙 결함이 아님 (INT8은 원본을 충실 미러링). **시사점: "엔티티 0개 = 쉬운 정형문"이 아니므로 M4의 T0 판정은 NER 결과 단독이 아니라 정형문 패턴 매칭과 결합해야 한다.**

## 배치 처리량 (M2, 2026-09-01)

- 경로: 배치 발행(BatchPump, 윈도우 3) → Redis Streams → 워커 → 적응형 rate 버킷 → `gemini-3.1-flash-lite`
- 조건: 골든셋 30문장 배치 × 2회, `SJW_RATE_INITIAL_RPM=60` (버킷 상한을 provider보다 높게 두고 실제 한계를 관찰)
- 재현: `N=30 OFFSET=110 ./deploy/demo-rate-control.sh` / 수치는 `cost_ledger`의 첫·끝 기록 시각 기준

| 구성 | 완료 | 실패 | LLM 호출 (원장) | 소요 | 처리량 |
|---|---|---|---|---|---|
| 워커 1대 | 30/30 | 0 | **정확히 30회** | 77s | **23.4 jobs/min** |
| 워커 2대 (버킷 공유) | 30/30 | 0 | **정확히 30회** | 78s | **23.1 jobs/min** |

**해석**
- **워커를 2배로 늘려도 처리량이 늘지 않는다 (23.4 → 23.1).** 병목이 워커 CPU가 아니라 외부 API 왕복이라는 D11(워커 단일 인스턴스 확정)의 실측 근거.
- 두 배치 모두 원장 기준 호출 수 = job 수 — 2워커 경합 상황에서도 **중복 호출 0건** (멱등 키 + 버킷 공유 동작 확인).
- 2워커 실험은 `SJW_RATE_MAX_WAIT_MS=20000` 오버라이드가 필요했다. 기본값(120s)이 stale claim 회수 주기(30s)보다 길어, 정상 대기 중인 워커의 메시지를 다른 워커가 회수해 중복 호출할 수 있기 때문 — 이 제약 자체가 D11의 두 번째 근거다.

## 적응형 rate control 검증 (M2, 2026-09-01)

수용 기준 "429 유발 시 rate 자동 하향, 회복 후 상향"의 증거 상태:

- **라이브로 확인된 것:** Redis Lua 토큰 버킷이 워커 2대를 단일 rate로 페이싱 (데모 타임라인의 `tokens`/`streak` 텔레메트리), 연속 성공 카운팅, 60 RPM 상한에서 30/30 완료.
- **라이브로 유발하지 못한 것:** 실제 429. 버킷 상한 60 RPM·워커 2대에서도 flash-lite의 유효 한도에 도달하지 않았다 (2회 시도 모두 429 0건). AIMD 하향(429→rate 절반)·상향(연속 5성공→+1 RPM)은 **실측 429 응답 원문을 사용한 리미터 단위 테스트**로 검증되어 있다.
- 더 강한 유발 수단(워커 3대+, RPM 추가 상향)은 D11 위배·quota 소진이라 시도하지 않는다. **강제 429 하의 라이브 검증은 M6 mock provider 부하 테스트로 이관** (계획서 §10 M6: "워커 다중화는 mock provider 하에서만 검증").
