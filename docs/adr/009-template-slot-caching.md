# ADR-009: 템플릿 슬롯 캐싱 및 KB 버저닝 무효화 전략 (§5.2)

- 상태: 승인 (M3-S1) · **개정 (M3-S2, 2026-09-10)**
- 날짜: 2026-09-01

## 배경

M3의 2단 캐시(L1 원문 완전 일치 / L2 템플릿 구조 일치)는 LLM 호출 자체를 제거하는
최대 절감 레버지만, 계획서 §5.2가 명시한 난제를 먼저 결정해야 한다:

1. **KB 갱신 시 무효화** — 인물 레코드가 수정되면 어떤 캐시가 무효화되어야 하는가.
   KB 수정의 현실적 사유는 대부분 **오링크 교정**이므로, 교정 전 결과가 캐시에 잔존해
   계속 서빙되는 것이 최악의 실패 모드다.
2. **재주입 시 한국어 조사 처리** — 슬롯의 인명이 바뀌면 뒤따르는 조사(이/가 등)의
   받침 일치가 깨진다.
3. **재주입 결과의 검증** — L2 히트는 LLM이 생성하지 않은 문장이다. 품질 증거가 필요하다.

전제(M2.5): `kb_version`·`prompt_version`은 파일 체크섬 파생값이라 데이터가 바뀌면 값이
반드시 바뀐다 (ADR-023). 품질 게이트(ADR-019)가 결과마다 `quality_grade`를 판정한다.

## 선택지

**무효화:**
1. **A. 버전을 캐시 키에 포함** — KB·프롬프트가 바뀌면 키가 달라져 전면 무효화. 코드 0줄
2. B. 엔티티 ID → 캐시 키 역참조 인덱스 — 수정된 인물이 걸린 엔트리만 정밀 무효화
3. C. TTL만 — 시간이 지나면 알아서 소멸

**슬롯 범위:** 확정 PER만 / PER+POS+DAT 전부

## 결정

**무효화는 A안: `cache:l1:{kb_version}:{prompt_version}:{ner_version}:{epoch}:{normalized_hash}`,
`cache:l2:{kb_version}:{prompt_version}:{ner_version}:{epoch}:{template_hash}`.**
(`ner_version`·`epoch`은 2026-09-10 개정에서 추가 — 아래 개정 절 참조)

- §8.3 초안은 L1 키에 버전이 없었으나 **L1에도 버전을 넣는다**. L1 값에는 번역문뿐 아니라
  KB 파생물(링크된 엔티티, resolvedName)이 통째로 들어 있고, KB 갱신 = 오링크 교정이라면
  L1의 교정 전 결과 잔존이 정확히 배경 1의 실패 모드다. prompt_version도 같은 이유 —
  프롬프트 개정 후 옛 스타일 결과가 서빙되면 기준선 비교(§5.4)가 오염된다.
- 버전이 체크섬 파생이므로 무효화는 **배포·재기동 없이 키 변경으로 저절로** 일어난다.
  옛 버전의 고아 엔트리는 TTL 30일이 회수한다 (TTL은 정확성 장치가 아니라 메모리 위생).
- **슬롯 범위는 링크 확정 PER만 (v1).** 재주입의 안전성은 "이 자리에 들어갈 문자열"을
  결정론적으로 아는 데서 나오는데, 그 답(KB 확정 한글명)을 가진 타입이 PER뿐이다.
  POS·DAT는 결정론적 한국어 대역이 없어 문면 그대로 템플릿에 남는다.
- **적재 정책이 품질 방어선이다**: L1은 게이트 통과분만(VERIFIED/DEGRADED — 등급 보존,
  REJECTED 미적재), L2는 **VERIFIED + 모든 슬롯의 한글명 전체형이 번역문에 출현**할 때만.
  게이트가 이름부 일치("문회")도 반영으로 인정하는 것과 달리, 템플릿화는 인명 구간을
  특정해야 하므로 전체형만 허용한다 (보수적 적재 = 히트율을 조금 버리고 안전을 산다).
- **조사 보정 (배경 2)**: 마커 바로 뒤의 조사 5쌍(이/가, 을/를, 은/는, 과/와, 이라/라)을
  새 인명의 받침에 맞게 교정한다. 단음절 조사는 뒤가 한글이면 다음 단어의 첫 글자일 수
  있어("○○이조판서") 경계(공백·구두점·문장 끝)일 때만 보정한다. 구조 불일치(마커
  누락·잔존)는 히트 취소 → MISS로 전체 파이프라인 fallback (M3 수용 기준).
- **L1 키에 모델은 넣지 않는다.** 모델 선택은 서버 몫이고(클라이언트 계약 아님), 적재가
  게이트 통과분뿐이라 품질 하한이 이미 보장된다. 생산 모델은 값의 meta에 보존해 반환한다.
- L2 히트 결과는 `DEGRADED`로 표시하고(§5.4 표), **기본 off, 명시 opt-in** — §5.4 비열등
  임계(chrF −2.0, 확정 인명 재현율 하락 0)를 통과해야 켠다 (배경 3, M3-S5에서 실측).

## 버린 대안과 그 이유

- **B(역참조 인덱스)**: 엔트리마다 걸린 인물 ID 색인을 유지하는 쓰기 비용·복잡도를 지는데,
  KB 갱신은 파일 교체 단위의 드문 이벤트다. 정밀 무효화가 아끼는 것은 "갱신 직후의 캐시
  워밍 비용"뿐이고, 이 시스템의 히트 대상(의례 정형문)은 재적재가 싸다. 수혜 없는 정밀함.
- **C(TTL만)**: "언젠가 사라진다"는 정확성 보장이 아니다. 오링크 교정 후에도 TTL 만료까지
  잘못된 인명이 서빙된다 — 배경 1을 정면으로 위반.
- **PER 외 타입 슬롯화**: POS를 슬롯화하면 히트율은 오르지만 재주입할 한국어 관직명의
  정본이 없다 (같은 관직도 문맥별 역어가 갈린다). 잘못된 재주입은 캐시가 아니라 오역 생성기다.

## 재검토 조건

- KB가 부분 갱신(개별 인물 교정)을 자주 받는 운영 단계에 들어가면 B안 재평가.
- L2 표본 재검증(§5.4)에서 조사 보정 실패·재주입 오류가 관측되면 보정 규칙 확장 또는 L2 축소.
- 관직 역어 사전이 생기면(연구 확장) POS 슬롯화 재평가.

## 개정 (M3-S2, 2026-09-10): 파이프라인 버전으로 확장

### 무엇이 빠져 있었나

원결정의 키는 `kb_version`·`prompt_version` 둘만 담았다. 그런데 번역 품질을 결정하는 축은
넷이다 — 인물 사전, 지시문, **NER 모델**, 번역 LLM. 그중 NER 모델에는 버전 개념이 아예 없었다
(`EntityRecognizer.id()`는 `onnx-http` 같은 고정 문자열이라 재학습본으로 갈아끼워도 그대로다).

이게 배경 1과 같은 종류의 실패다. NER이 좋아졌다는 것은 **예전엔 못 찾던 인명을 이제 찾는다**는
뜻인데, 캐시는 "이 원문 본 적 있음" 하고 옛 답을 그대로 내준다. 모델을 개선했는데 개선분이
캐시에 막혀 나타나지 않고, 그 엔트리는 옛 기준으로 이미 게이트를 통과한 상태라 등급으로도
드러나지 않는다 — **조용히** 손해를 본다. 인명 정확도가 이 프로젝트의 존재 이유이므로
그냥 둘 수 없다. NER 재학습은 가정이 아니라 예정된 개선 경로다(백본 `ddokbaro/SillokBert-NER`).

### 결정

- **키를 파이프라인 버전으로 확장한다**: `{kb_version}:{prompt_version}:{ner_version}:{epoch}`.
  `PipelineVersion`/`PipelineVersions`(common/cache)가 조립하고, 하나라도 비면 캐시는 쉰다.
- **`ner_version`은 모델 파일에서 파생한다.** NER 서버가 `model.onnx` + `config.json`의
  SHA-256 앞 8자리를 `/healthz`의 `model_version`으로 노출하고(`onnx-3f2a9c1e` 꼴),
  HTTP 어댑터가 첫 사용 시 받아 고정한다. KB·프롬프트와 같은 체크섬 파생 방식이라
  "버전 올리는 걸 깜빡"할 수가 없다 — 이 프로젝트가 자유 문자열 버전을 신뢰하지 않는 이유
  그대로다(ADR-023, `KnowledgeSource.version()` 계약).
- **번역 LLM은 여전히 키에 넣지 않는다** (원결정 유지). 대신 **`epoch`을 수동 손잡이로 둔다**
  (`sjw.cache.epoch`, 기본 1). 모델을 갈아끼우고 캐시를 전면 재구축하려면 이 값을 올린다.
- **세그먼트를 해시로 뭉치지 않는다.** 키만 보고 무엇이 캐시를 가르고 있는지 읽을 수 있어야
  한다 — 저절로 일어나는 무효화일수록 눈으로 확인 가능해야 한다.

### 이 개정이 만드는 부수 효과 (의도된 것)

`NER_MODE`를 `http`↔`rule`로 바꾸면 버전이 달라져 캐시가 갈린다. 골든셋 recall 26.9%짜리
규칙판 결과와 100%짜리 ONNX 결과가 한 캐시에 섞이면 안 되므로 이게 옳다.

한 번 버전을 받아둔 뒤 NER 서버가 죽으면 값은 유지된다 — **지식 계층 장애 중에도 이미 캐시된
문장은 계속 서빙된다.** 반대로 한 번도 못 받은 상태에서는 캐시가 조회·적재를 모두 건너뛴다.
불확실한 키로 캐시를 오염시키느니 미스가 낫고, 어차피 그 요청은 `NER_UNAVAILABLE`로 실패한다.

### 버린 대안

- **LLM 모델도 키에 포함**: 무엇이 바뀌든 자동이라 제일 안전해 보이지만, 모델을 실험 삼아
  몇 번 갈아끼울 때마다 캐시가 전멸한다. 무료 티어(RPD 20)에서 재구축 비용은 곧 하루치 quota다.
  모델 선택은 서버 몫이고 적재가 게이트 통과분뿐이라 품질 하한은 이미 보장된다 — 자동일
  필요가 없는 축이다.
- **`epoch` 하나로 전부 처리(수동 일원화)**: 제일 단순하지만 올리는 걸 깜빡하면 옛 결과가
  조용히 계속 나간다. 체크섬으로 자동화할 수 있는 축까지 사람 기억에 맡길 이유가 없다.
- **모델 목록 자동 감지 + 자동 전환**: 품질이 바뀌는 교체를 검증 없이 자동화하는 셈이라
  이 프로젝트의 전제(§5.4 비열등)와 충돌한다. 감지·재채점은 결과 DB가 생기는 M6에서
  CI에 붙인다(`eval/score_db.py`의 종료 코드 계약이 이미 그 용도로 준비돼 있다).

### 재검토 조건 (추가)

- NER 재학습이 잦아져 무중단 교체가 필요해지면, 버전 확보를 "첫 사용 시 1회 고정"에서
  주기 갱신으로 재평가한다 (현재는 모델 파일 교체 = 재기동이라는 규약에 기대고 있다).
