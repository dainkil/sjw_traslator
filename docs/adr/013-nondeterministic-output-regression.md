# ADR-013: 비결정 LLM 출력의 회귀 검증 — 결정론 축은 CI, 확률 축은 사전 고정 임계의 오프라인 배치

- 상태: 승인 (M2.5-S7에서 기준선 확보 · M3.5-S1에서 채점기 확장 · M3.5-S2에서 첫 전면 적용)
- 날짜: 2026-09-21 (참조는 2026-09-01부터 — `PromptAssembler`, V4 마이그레이션, ADR-007, 계획서 §4.2·§5.4)

## 배경

프롬프트·패턴·KB·NER·모델 중 하나만 바뀌어도 번역이 바뀐다. 그런데 "바뀌었다"를 CI가 잡으려면 두 가지가
동시에 성립해야 한다: ① 무엇이 바뀌었는지 결정론적으로 식별할 수 있어야 하고 ② 품질이 나빠졌는지를 잴 수
있어야 한다. 이 프로젝트에서 ②는 CI 안에서 할 수 없다 — CI는 LLM을 호출하지 않는다(ADR-016, 무료 quota 보존).
그리고 LLM 출력 자체가 비결정이다. 실측(M3.5-S2, temperature 0.2, flash-lite):

- 같은 프롬프트로 60문장을 3라운드 돌리면 **20문장만 번역문이 동일**하고 40문장은 표현이 흔들린다.
  corpus chrF 폭은 0.69(v0 3라운드), L2 판정 때는 3.0(단일 라운드 −2.20이 임계를 넘었다가 중앙값으로 통과).
- **인명은 흔들리지 않는다** — ETS 누락 3건(유황·안위·박군)이 세 라운드 동일, 게이트 등급 분포도 동일.

즉 "같은 입력 = 같은 출력"을 전제하는 스냅샷 회귀는 성립하지 않고, 문체 축은 확률적, 인명 축은 결정론적이다.

## 선택지

1. **결정론 축은 CI에서, 확률 축은 오프라인 배치에서 — 사전 고정 비열등 임계 + 3회 중앙값 + 배치 단위 채점**
2. CI에서 골든셋을 LLM으로 번역해 회귀 판정
3. 번역문 exact-match 스냅샷 회귀

## 결정

**선택지 1.** 구성 요소와 실체:

**(1) 결정론 축 — 바뀌었는지는 CI가 안다.**
- 프롬프트 템플릿·패턴은 리소스 파일이고 `prompt_version = "main-" + SHA-256(template ++ patterns)[:8]`
  (`PromptAssembler.version()`). 1바이트 차이가 다른 버전이다. KB(`kb_version`)·NER(`model_version`)도 같은 규칙.
- 이 버전들이 job 행(V4 `prompt_version`)·응답 meta·L1/L2 캐시 키(`{kb}:{prompt}:{ner}:{epoch}`)에 남는다 —
  무효화 코드 없이 캐시가 갈리고, 어느 결과가 어느 프롬프트로 만들어졌는지 사후 추적된다.
- 프롬프트 조립은 결정론적이다(패턴 파일 순서 고정, `PromptAssemblerTest` "같은 입력은 같은 프롬프트").
  Tool Calling·ChatMemory를 배제한 이유의 절반이 이것이다(ADR-007·008).
- **CI 게이트** `eval/tests/test_prompt_version_gate.py`: 생산 프롬프트의 체크섬이 `eval/baseline_scores.json`의
  `prompt_versions`에 없으면 실패. "프롬프트를 고쳤는데 기준선을 다시 재지 않았다"를 잡는다. 기준선 갱신은
  변경을 확정할 때만 `score_db.py --prompt-version <v> --save-baseline`(ADR-019와 같은 규칙 — 무단 갱신은 게이트 무력화).
- 채점기·드라이버 단위 테스트(`eval/tests/`)가 CI `eval-tests` 잡에서 돈다: Java `TextHash`가 쓴 행으로 해시 파리티,
  ETS·반영률 규칙, 정답 번역 자체의 ETS 상한 0.9713 재현, 층화 표본 재현성.

**(2) 확률 축 — 나빠졌는지는 오프라인 배치가 잰다.**
- 임계는 **측정 전에 고정**한다(§5.4): chrF 기준선 대비 −2.0 이내, 주입 인명 반영률 하락 0, ETS 하락 ≤ 대조군
  라운드 간 폭(M3.5-S2에서 0.0000으로 실측·고정). 사후에 정하면 게이트가 아니다.
- **3회 반복 중앙값** — LLM 비결정성을 흡수한다. 단일 라운드 판정이었으면 L2는 어떤 날은 합격, 어떤 날은 불합격했다.
- **배치 단위 채점** — `score_db.py --batch-id`(라운드 = 배치), `--prompt-version`(버전별 기준선). 결과가 섞이지 않는다.
- **대조군 선행 강제** — `prompt_ablation.py`는 v0 3라운드가 끝나 임계가 파일에 박힌 뒤에만 변형을 채점한다.
- **self-check** — 드라이버가 파일 바이트로 계산한 기대 버전과 DB 행의 `prompt_version`을 대조, 불일치면 pause·exit 2.
  Java↔Python 파리티는 이 라이브 대조가 증명한다(단위 테스트로는 Java 값이 없어 불가). 실측 `main-d5ac24e9` 일치.
- **모델 고정·캐시 off** — 실험 중 품질 승격(REJECTED→3.5-flash)과 L1/L2를 끈다. 승격은 표본에 두 모델을 섞고
  나쁜 프롬프트를 상위 모델이 구제해 효과를 가리며, 캐시는 2·3라운드의 분산을 0으로 만든다(둘 다 실측된 함정).

## 버린 대안과 그 이유

- **(2) CI에서 LLM 호출**: 골든셋 60 × 3라운드 = 180회를 push마다 태우면 무료 quota(500/일)의 36%다. 유료여도
  비결정성이 남아 같은 커밋이 어떤 날은 빨갛다 — L2 판정 1차 R1(−2.20)이 그 사례. 정확히 "CI가 흔들린다"는 상태.
- **(3) exact-match 스냅샷**: 60문장 중 40문장이 매 실행 다르다. 항상 실패하는 테스트는 테스트가 아니다.
  결정론적인 인명 축에 한해서는 성립하지만, 그것은 이미 런타임 게이트(ADR-019)와 ETS가 잰다.

## 재검토 조건

- 유료 전환 또는 전용 평가 quota가 생기면 (2)를 **야간 스케줄 잡**으로 붙인다 — 종료 코드 계약은 이미 CI-호환이다
  (`score_db.py` 위반=1). 배포 타겟 DB가 생기는 M6이 그 시점이다.
- 라운드 간 chrF 폭이 임계(2.0)를 넘는 모델이 오면 3회로는 부족하다 — 라운드 수를 폭/임계 비율로 재산정한다.
- ETS 허용 하락폭 0은 대조군 실측값이다. 인명이 라운드 간 흔들리는 모델·프롬프트가 나타나면 그 폭으로 갱신한다
  (역시 변형 채점 전에).

## 적용 기록 — M3.5-S2 프롬프트 채택 (2026-09-24)

첫 실전 적용. 여섯 변형 × 3라운드 × 60문장, 전부 사전 고정 임계 통과(`eval/prompt_ablation.json`, benchmarks 해당 절).

- **사전 규칙의 선택은 v2**(통과 변형 중 tokens_in 최소, −13.6%, 품질 v0와 동일). 판정 파일에 그대로 둔다.
- **채택은 v4**(`main-4a1cb192`, −11.2%) — 소유자 결정. v4는 chrF +2.42·ETS +1명·REJECTED 0으로 품질 세 지표가 모두
  오른 유일한 저토큰 변형이고, v2 대비 대가는 +22 tok다. 규칙은 "통과 변형들의 품질이 같다"를 암묵 전제했는데 측정이
  그 전제를 깼다. **규칙을 사후에 고치지 않고, 규칙의 답과 채택을 나란히 기록한다** — 사후 임계 금지의 취지(결과를 보고
  기준을 움직이지 않는다)는 판정 기록이 보존되는 한 지켜진다고 본다. 다음 ablation부터 결정 규칙은 "통과 변형 중
  품질 지표 우위가 라운드 범위 밖이면 그것, 아니면 토큰 최소"처럼 품질 차이를 먼저 보도록 **실험 전에** 바꾼다.
- 결정론 축 게이트가 이 채택으로 처음 켜졌다: `baseline_scores.json`을 v4 결과(층화 60, 라운드 3)로 재저장
  → `test_prompt_version_gate`가 skip에서 활성으로. `translate-main.st`는 `eval/prompts/v4-minimal.st`와 바이트 동일.
