# ADR-004: KB in-memory 유지 — Redis 외부화 배제

- 상태: 승인 (M1에서 구현, M2.5에서 기록)
- 날짜: 2026-09-01

## 배경

엔티티 링킹 KB(인조 연간 인물 2,690 레코드 + 역색인 9,403키, 파일 합계 ~2MB)를 어디에 둘 것인가.
"워커는 무상태여야 하니 공유 저장소로" 라는 상투적 결론(D4)이 실제로 옳은지 확인이 필요했다.

## 선택지

1. **JVM in-memory** — 기동 시 JSON 로드, HashMap 조회
2. Redis 외부화 — 해시/세트로 적재, 링킹마다 네트워크 조회
3. Postgres 테이블 — SQL 조회

## 결정

**선택지 1.** 근거:

- 링킹 실측 **≤1ms** (docs/benchmarks.md E2E 분해). 외부화하면 엔티티마다 네트워크 왕복이 붙어 유일한 효과가 "느려짐"이다.
- 무상태성 논점의 오류: KB는 **불변 읽기 전용 데이터**라 상태가 아니다. 워커 간 공유가 필요한 것은 변하는 상태(큐, rate 버킷, 예산 카운터)뿐이고, 그것들만 Redis에 있다 (D5).
- 수 MB는 로드 1초 미만. 배포 시 파일과 함께 굴러가므로 정합성 문제도 없다.

## 버린 대안과 그 이유

- **Redis(2)**: 공유로 얻는 것이 0인데 왕복 지연 + 직렬화 비용 + "KB 적재됐나"라는 새 운영 체크포인트가 생긴다. 근거 없는 외부화 = 오버엔지니어링으로 면접에서 찔리는 자리.
- **Postgres(3)**: 조인·트랜잭션이 불필요하고, 역색인 조회 패턴은 해시맵이 정확히 맞는 자료구조다.

## 재검토 조건

- KB가 전 왕대(수십만 레코드, 수백 MB급)로 확장되어 기동 로드가 유의미해지면.
- 여러 이질 서비스가 동일 KB를 소비하게 되면. 그 시점의 교체 지점은 M2.5의 `KnowledgeSource` 포트가 이미 만들어 둔다 (ADR-018).
