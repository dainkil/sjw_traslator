# ADR-001: 비동기 큐 기반 처리 채택 (동기 요청/응답 배제)

- 상태: 승인 (M2에서 구현)
- 날짜: 2026-08-31

## 배경

M1 실측으로 전체 p95의 **99.7~99.9%가 외부 LLM**임이 확정됐다 (docs/benchmarks.md). 동기 처리면 API 스레드가 요청당 2~19초씩 남의 지연에 묶이고, 수백~수천 문장 배치는 아예 성립하지 않는다. 무료 티어(ADR-016)의 일일 quota는 배치가 **여러 날에 걸쳐 중단·재개**될 것을 구조적으로 강제한다.

## 선택지

1. **비동기 큐**: API는 202+jobId 반환, Worker가 소비 (계획서 D1)
2. 동기 처리 + 대형 스레드풀/가상 스레드
3. 서버리스 함수 팬아웃

## 결정

**선택지 1.** 구현 형태 (M2):

- 스트림 메시지에는 **jobId만** 싣고 본문·상태·결과는 PostgreSQL — 재전달이 안전하고, 큐는 신호 전달만 담당.
- 전달 보장은 **at-least-once**: 처리 완료/스킵 시에만 XACK. 크래시 시 pending으로 남고 재기동 워커가 claim해 이어간다.
- 중복 처리 방어는 DB가 담당: `SUCCEEDED/DEAD면 스킵` + LLM 호출 원장(cost_ledger)으로 "저장된 job의 재호출 0건"을 증명 (deploy/demo-resume.sh).
  - 정직한 경계: LLM 응답 수신~저장 사이에 죽는 in-flight 1건은 재실행된다 (at-least-once의 본질). exactly-once를 흉내내려면 외부 API 호출에 분산 트랜잭션이 필요한데 존재하지 않는다.
- 배치는 **펌프 모델**: job 행을 생성 시 전부 만들고, Worker의 BatchPump가 커서부터 소량 윈도우로 발행. 일시정지=발행 중단, 재개=커서부터, 예산(호출 수)은 원장 실측으로 강제.
- DB 접근은 JPA 대신 **JdbcClient(스프링 내장)**: 스키마가 4테이블로 작고 질의가 명시적이며, 엔티티 매핑·영속성 컨텍스트가 줄 게 없다. 추가 의존성은 starter-data-jdbc/-redis, postgresql 드라이버.

## 버린 대안과 그 이유

- **동기+가상 스레드(2)**: 스레드는 싸졌지만 문제는 스레드가 아니라 **수명**이다. 배치 중단·재개, 예산 통제, 실패 분류는 요청-응답 수명 밖의 상태를 요구한다. 가상 스레드는 D1의 "배치 유스케이스 성립 불가"를 해결하지 못한다.
- **서버리스(3)**: 이 규모(단일 호스트, 무료 quota가 상한)에 콜드스타트·상태 외부화 비용만 추가. NER 모델 상주와도 상성이 나쁘다.

## 재검토 조건

- 단건 대화형 트래픽이 지배적이 되고 배치가 사라지면 동기+SSE 단일 경로로 축소를 검토.
