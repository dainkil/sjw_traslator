# ADR-014: 큐 기술 선택 — Redis Streams (vs RabbitMQ, vs Kafka)

- 상태: 승인 (M2에서 구현)
- 날짜: 2026-08-31

## 배경

ADR-001이 비동기 큐를 확정했다. 큐 기술을 골라야 한다. Redis는 §3.1에서 이미 캐시·rate 상태·예산 카운터로 필요한 상태다.

## 선택지

1. **Redis Streams** (Consumer Group + XACK + XCLAIM)
2. RabbitMQ
3. Kafka (계획서 §7에서 선배제)

## 결정

**선택지 1.** 근거:

- **운영 표면적이 0 증가.** Redis는 캐시(M3)·적응형 rate 버킷(M5)·예산 카운터(M5) 때문에 어차피 뜬다. 큐 하나 때문에 브로커 프로세스를 하나 더 운영하는 것은 이 규모(수만~수십만 메시지)에서 순손실.
- 필요한 보장이 전부 있다: Consumer Group(경쟁 소비), XACK(수동 확인), XPENDING/XCLAIM(죽은 소비자 회수), XADD(영속 로그). M2 데모(강제종료→재개)가 이 프리미티브만으로 동작함을 증명했다.
- 워크로드가 **큐 깊이보다 외부 API rate에 지배**된다 — 처리량 상한은 브로커가 아니라 무료 quota다. 브로커 성능 차이가 무의미한 지점.

## 버린 대안과 그 이유

- **RabbitMQ(2)**: 라우팅 토폴로지(exchange/binding), per-message TTL, 우선순위 큐가 필요했다면 옳은 선택. 본 워크로드는 단일 스트림 + DLQ 1개로 충분해서 그 기능들이 전부 유휴 자산이 된다. 반면 비용은 실재한다: 브로커 운영, Erlang 런타임, 클라이언트 재연결 처리.
- **Kafka(3)**: 파티션 병렬성과 리플레이가 핵심 가치인데, 병렬성 상한은 외부 API quota(수십 RPM)라 파티션이 무의미하고, 리플레이는 Postgres의 job 테이블이 이미 제공한다. §7의 선배제 그대로 확정. "왜 Kafka 아니냐"는 질문의 답: **처리량 병목이 큐가 아니라는 실측**(docs/benchmarks.md)이 있다.

## 재검토 조건

- 유료 전환 + 동시성 수백 이상으로 올라가 큐 자체가 병목으로 실측되면 재검토.
- 메시지 유실이 허용 불가능한 과금 이벤트를 큐로 옮기게 되면 (현재는 원장이 DB) 브로커 영속성 요구를 재평가.
