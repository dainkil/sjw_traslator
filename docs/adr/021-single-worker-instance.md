# ADR-021: 워커 단일 인스턴스 확정 — 다중화 배제와 재검토 조건

- 상태: 승인 (D11, 2026-09-01 계획 개정에서 확정)
- 날짜: 2026-09-01

## 배경

M2-S5의 rate 버킷은 Redis Lua라 워커 여러 대가 공유할 수 있게 만들어져 있다. 그렇다면 워커를 늘려야 하는가?
S6에서 2워커 실험을 실제로 수행해 데이터로 답했다.

## 실측 (docs/benchmarks.md, 2026-09-01)

| 구성 | 처리량 | 중복 호출 |
|---|---|---|
| 워커 1대 | 23.4 jobs/min | 0건 |
| 워커 2대 (버킷 공유) | 23.1 jobs/min | 0건 |

**워커를 2배로 늘려도 처리량이 늘지 않는다.** 병목이 워커 CPU가 아니라 외부 API 왕복(전체 p95의 99.7%+)과 공유 rate 상한이기 때문이다.

또한 현 구현의 안전 파라미터가 다중화와 양립하지 않는다: stale claim 회수 주기(30s)가 permit 대기 상한(`max-wait-ms` 120s)보다 짧아, 버킷이 마른 상황에서 **정상 대기 중인 워커의 메시지를 다른 워커가 죽은 것으로 오인해 회수 → 중복 LLM 호출 = 중복 과금**이 발생할 수 있다. 2워커 실험은 `SJW_RATE_MAX_WAIT_MS=20000` 오버라이드로 이 창을 닫고 수행했다.

## 선택지

1. **워커 단일 인스턴스 확정**
2. 다중화 허용 + 파라미터 조정 (stale 회수 > 대기 상한이 되도록 150s+)
3. 다중화 허용 + fencing 토큰으로 중복 호출 차단

## 결정

**선택지 1.** 처리량 이득이 실측 0인데, (2)(3)은 각각 복구성 희생과 정합성 기계 추가라는 실비용을 낸다. 이득 0에 비용을 지불하지 않는다.

## 버린 대안과 그 이유

- **(2) 파라미터 조정**: stale 회수를 150s+로 늘리면 진짜 죽은 워커의 작업 복구가 2.5분 이상 지연된다. 얻는 것 없는 다중화를 위해 장애 복구 시간을 파는 거래.
- **(3) fencing**: 원장 기반 중복 감지 + 호출 전 소유권 재확인을 추가로 구현해야 한다. quota가 병목인 한 이 기계가 지킬 이득이 없다.

## 재검토 조건

- 유료 전환 등으로 rate 상한이 수백 RPM대가 되어 **단일 워커의 직렬 처리(호출당 ~3s 점유)가 병목으로 실측**되면 다중화한다. 그때 반드시 함께 고칠 것: ① stale 회수 주기 > permit 대기 상한 보장 ② 호출 직전 소유권 재확인(또는 fencing) ③ 버킷 burst 파라미터 재산정. 이 목록이 이 ADR의 절반이다 — "늘리면 되지"가 아니라 늘릴 때 무엇이 깨지는지를 기록해 둔다.
- k6 부하 테스트(M6)는 mock provider 하에서 다중화를 검증한다 (§10 M6).
