## 1. 프로젝트 목적

### 무엇을 만들었나

**한문 원문(《승정원일기》)을 한국어로 번역하는 생성형 서빙 시스템**이다. 입력 문장에서 인물명을 찾아(NER) 인물 사전(KB)으로 누구인지 확정하고, 그 정보를 프롬프트에 넣어 LLM이 번역하게 한 뒤, **확정한 인명이 번역문에 실제로 반영됐는지 매 응답마다 판정**해 VERIFIED / DEGRADED / REJECTED 등급을 붙인다.

### 왜 이 문제를 골랐나

- **규모의 문제.** 《승정원일기》는 2억 4,250만 자 규모의 세계 최대 단일 역사 기록물이지만 국역 완료율은 **37.4%**다. 지금 속도라면 완역은 **2062년**에 끝난다.
- **정확도의 문제.** 기존 고전 한문 번역 모델은 고유명사 번역 정확도가 **8.3%**에 머물렀다. 역사 번역에서 인명 오역은 번역 실수가 아니라 **기록된 사실을 바꾸는 오류**다. 게다가 결과 문장이 자연스러워서 **검수자도 놓치기 쉽다.**
- **문제 재정의.** 범용 LLM은 이미 문장을 자연스럽게 옮긴다. 남은 문제는 "번역을 더 잘하게"가 아니라 **"인명 오류를 통제하게"**였다. 그래서 문제를 둘로 나눴다.

| 하위 문제 | 담당 | 이유 |
|---|---|---|
| **언어 변환** — 한문 문장을 한국어로 | LLM | 범용 LLM이 이미 잘한다 |
| **사실 복원** — 이 한자가 누구이고 어떻게 읽는가 | NER + 인물 KB | 모델 가중치에 외우게 하는 대신 **검증 가능한 사전**에서 확정한다. 인물 추가·수정이 재학습이 아니라 데이터 작업이 된다 |

### 서빙 관점의 목표

E2E 지연을 단계별로 분해하자 **p95 지연의 99.7~99.9%가 외부 LLM API**였다(NER 8ms, KB 조회·프롬프트 조립 1ms 이하). 우리 코드를 빠르게 만드는 것은 의미가 없었고, 목표는 세 가지로 좁혀졌다.

1. **LLM 호출 자체를 줄인다** — 캐싱, 프롬프트 다이어트
2. **느리고 불안정한 외부 호출을 잘 기다린다** — 비동기 큐, 적응형 속도 조절, 중단 후 재개
3. **품질을 깎는 최적화는 품질 증거 없이 켜지 않는다** — 비열등 게이트

### 데이터 출처와 규모

| 자산 | 규모 | 출처 · 용도 |
|---|---|---|
| 병렬 코퍼스 | 62,476쌍 (인조 연간) | [승정원일기 DB](https://sjw.history.go.kr/)의 한문 원문 ↔ 전문가 국역. 캐시·라우팅 시뮬레이션과 통계 |
| 골든셋 | 300문장 | 원문 + 전문가 번역. 품질 평가 기준 |
| 인명 정답지 | 188문장 · 383명 | 국사편찬위원회 사이트의 인물 어노테이션 — **시스템과 독립된 정답** |
| 인물 KB | 2,690명 · 역색인 9,403키 | 한자 표기 → 한글명·활동 시기·관직. 전 시대 27,329명 중 인조 구간 |
| 층화 평가셋 | 60문장 · 정답 인명 104명 | 골든셋에서 정형 패턴 × 문장 길이로 층화 추출(seed 42). 통제 실험 전용 |

### 품질·전처리 이슈 — 이상한 측정값을 끝까지 추적해서 찾았다

| 이슈 | 발견 경위 | 처리 |
|---|---|---|
| **원문–번역 정렬 결함 (11.24%)** | 품질 게이트를 코퍼스 전체에 적용하자 REJECTED가 26.6% — 골든셋 측정치 3.9%의 7배. 게이트 버그를 의심했지만 행을 열어 보니 **번역이 한 줄씩 밀려 이웃 문장의 번역이 붙어 있었다** | "확정 인명이 자기 번역엔 없고 이웃 번역엔 전부 있으면 밀린 짝" 규칙으로 검출·제외 → 오탐률 **4.36%로 골든셋 값과 일치**. 코퍼스를 정답으로 쓰는 모든 측정에서 먼저 거른다 |
| **정답 코퍼스의 표기 관행** | 정답 300문장은 전부 `아뢰기를,“…”하니,`(둥근 따옴표, 띄어쓰기 없음)인데 프롬프트 예시는 `아뢰기를, "…" 하니,` | 글자 단위 지표(chrF)가 이 차이만으로 깎인다. 이후 프롬프트 실험의 핵심 변수가 됐다 |
| **KB 커버리지 공백** | 12만 건의 인명 멘션을 링킹하면 확정 61.9%, **사전에 없음(MISS) 36.5%**, 동명이인 1.1% | MISS의 87%가 2~3자 실명 → NER 오검출이 아니라 진짜 사전 공백. 빈도 10회 이상 표면형만 채워도 MISS의 42%가 해소됨을 계산해 KB 확장 목록으로 정리 |

### 라벨 상태

- **NER 학습 라벨은 silver label**이다. 사람이 붙인 라벨이 아니라 모델이 생성한 신뢰도 0.9 이상의 라벨로 학습됐다. 그래서 `領議政李元翼`처럼 명백한 인명 문장에서 모든 토큰을 "개체 아님"으로 예측하는 경우가 관찰됐다. → "엔티티 0개 = 쉬운 정형문"이라는 라우팅 가정을 버리고 **NER 결과와 정형문 패턴 매칭을 결합**했다.
- **순환 지표를 걷어냈다.** 초기 헤드라인이던 "인명 반영률 99.09%"는 *시스템이 프롬프트에 넣은 이름이 번역에 살아남았는가*를 셌다. 주입 소스와 채점 소스가 같아서 KB가 이름을 **틀리게** 확정해도 100%가 나오는 구조다. 이 값은 게이트 지표로 강등하고, **독립 정답지 기반 ETS**(Entity Translation Score, 정답 인명이 번역문에 올바르게 들어간 비율)를 품질 지표로 새로 세웠다.

### 편향과 제약

| 구분 | 내용 | 영향 |
|---|---|---|
| **시대 편향** | KB·코퍼스·평가셋이 모두 **인조 연간(1623–1649)** | 다른 왕대는 KB 교체가 필요하다(정조 KB는 준비돼 있고 설정만으로 교체 가능하게 설계) |
| **평가셋 편향** | 평가셋은 KB가 아는 인물 비중이 높다 | 사전에 없는 인물이 많은 문장의 품질은 아직 따로 측정하지 않았다 |
| **단일 참조 번역** | chrF는 전문가 번역 **하나**와의 표면 유사도 | 사람이 판정하는 번역 품질과 다르다. 그래서 인명은 ETS로 따로 잰다 |
| **운영비 0원** | 무료 티어 + 사용자 키(BYOK)만 사용 (ADR-016) | 모델별 일일 한도(예: flash-lite 500회, 상위 모델 20회)가 모든 설계의 제약이 됐다 |

## 4. 접근 방법

### 4.1 파이프라인

```
한문 원문 ─▶ ① NER (SillokBERT, ONNX INT8)        "兪榥은 인명이다"
            ② KB 링킹 (역색인 → 활동 시기 → 관직)    "兪榥 = 유황" 확정
            ③ 캐시 조회 (L1 원문 일치)                히트 시 LLM 없이 즉시 응답
            ④ 프롬프트 조립                           예시 + [등장 인물: 兪榥→유황]
            ⑤ LLM 번역 (Gemini)                       Structured Output(JSON)
            ⑥ 품질 게이트                             확정 인명이 번역문에 반영됐는가
                                                       VERIFIED / DEGRADED / REJECTED
─▶ 번역 + 비용·토큰 원장 기록

서빙:  API ─▶ Redis Streams ─▶ Worker (단일) ─▶ NER 서버 · Gemini
       PostgreSQL (결과·비용 원장) · Redis (캐시·속도 버킷·일일 한도)
```

NER은 이름이 **어디에** 있는지, KB는 그 이름이 **누구이고 어떻게 읽는지**를 정한다. 띄어쓰기가 없는 한문에서는 사전만으로 이름의 경계를 알 수 없고, NER만으로는 한글 표기와 동명이인을 알 수 없다.

### 4.2 기준 모델 — 모든 개선은 명시적 baseline 대비로만 주장했다

| 실험 | 기준 모델 | 비교 대상 | 고정한 것 |
|---|---|---|---|
| 지식 주입 효과 | **LLM 단독** (KB off) | NER + KB 파이프라인 | 모델, 프롬프트, 평가셋 60문장, 캐시 off |
| 프롬프트 최적화 | **v0** (기존 생산 프롬프트) | v1~v5 (구성 요소별 제거·교체) | 모델, KB, 평가셋, 캐시 off, 품질 승격 off |
| NER 경량화 | **PyTorch 원본** | ONNX fp32 / INT8 | 평가 문장 100개, CPU 단건 추론 |
| 템플릿 캐시 (L2) | **LLM 직접 번역** (같은 문장) | 캐시 틀에 인명만 재주입 | 정렬 검증된 1,220쌍 |
| 티어 라우팅 | **라우팅 없음** | 난이도별 모델 배정 | 전수 62,056문장 시뮬레이션 |

### 4.3 실험 설계 — 결과를 보고 기준을 바꾸지 않는다

LLM은 같은 입력에도 매번 다른 답을 낸다(60문장 중 40문장이 실행마다 표현이 달랐다). 비결정적인 대상을 공정하게 비교하려고 규약을 먼저 고정했다(ADR-013).

| 원칙 | 내용 |
|---|---|
| **임계값 사전 등록** | chrF −2.0 이내, 인명 하락 0 — 변형을 채점하기 **전에** 파일에 기록 |
| **3회 반복 중앙값** | 모든 조건을 3라운드 실행해 중앙값으로 판정 (1라운드만 봤다면 L2 실험이 −2.20으로 "위반" 판정을 받았을 것) |
| **대조군 선행 강제** | 드라이버가 v0 3라운드 완료 전에는 변형 채점을 거부 |
| **변수 격리** | 실험 중 캐시 off, 품질 승격 off (상위 모델이 나쁜 프롬프트를 구제하는 것 방지) |
| **자기 검증** | 결과 DB의 프롬프트 버전(파일 바이트 체크섬)을 기대값과 대조, 불일치 시 즉시 중단 |
| **생산 코드 경로** | 평가용 스크립트로 근사하지 않고 실제 서빙 파이프라인으로 번역 |

### 4.4 기술 선택과 이유

| 결정 | 버린 대안 | 근거 (실측) |
|---|---|---|
| NER을 **ONNX INT8 + CPU**로 서빙 | GPU 서빙 | INT8 p50 8.3ms. LLM이 지연의 99.7%인 구조에서 GPU의 ROI는 0에 수렴 |
| 인명 검색에 **벡터 DB/RAG 미사용** | 임베딩 유사도 검색 | 유사도 검색은 이 시스템이 없애려는 모호성(이름 경계, 동음이의)을 다시 들여온다. 결정론적 역색인 유지 |
| **Redis Streams** 비동기 큐 | 동기 API, Kafka | 남의 API 지연에 스레드를 묶지 않는다. 단일 노드 규모에서 Kafka는 운영 부담만 늘린다 |
| **품질 게이트 + 비열등 판정** | 검증 없이 최적화 활성화 | 캐싱·라우팅은 품질을 깎아 비용을 버는 기능이다. 추가 LLM 호출 0회로 매 응답 판정(오탐률 3.9%) |
| 캐시 키에 **파이프라인 버전** 포함 | 수동 무효화 | KB·프롬프트·NER 모델이 바뀌면 캐시가 저절로 갈린다. 무효화 코드 0줄 |
| **난이도 분류와 quota 배정 분리** | 난이도별 모델 고정 표 | 표대로면 완역이 124일 → 926일로 7.5배 늦어진다 |
| 워커 **단일 인스턴스** | 수평 확장 | 워커 2대의 처리량이 23.4 → 23.1 jobs/min으로 동일. 병목은 외부 API |
| **운영비 0원** (무료 티어 + BYOK) | 유료 API | 무료 quota를 예산 원장으로 삼고, 유료 비용은 파라미터 하나로 재계산되는 반사실 모델로 유지 |

전체 22건: [`docs/adr/`](docs/adr/)

## 5. 결과

### 5.1 지식 주입은 LLM 단독보다 얼마나 나은가

같은 모델·프롬프트·평가셋에서 **KB 주입만 켜고 끄며** 3라운드씩 측정했다.

| 지표 | LLM 단독 | 파이프라인 | 차이 |
|---|---|---|---|
| **ETS (인명 정확도)** | 90.4% (94/104) | **97.1% (101/104)** | **+6.7%p · 인명 오류 10 → 3** |
| chrF (문장 유사도) | 37.73 | 37.90 | 차이 없음 (라운드 범위 겹침) |
| 입력 토큰 | 867.5 | 917.9 | +5.8% (인물 블록 비용) |

> 지식 주입은 문장을 더 매끄럽게 만들지 않는다. 대신 **인명에만 정확히 작용해 오류의 2/3를 없앤다.** ETS는 세 라운드 모두 같은 값(90.4% ×3, 97.1% ×3)이 나왔다. 골든셋 독립 정답지 기준 전체 ETS는 **98.21%**(n=70)다.

**LLM 단독이 틀린 이름** — 모두 한국어로는 자연스러웠다. 검수로도 잡기 어려운 오류라는 뜻이다.

| 원문 | LLM 단독 | 정답 | 오류 유형 |
|---|---|---|---|
| 崔葕 | 최**헌** | 최**연** | 드문 한자 오독 |
| 朴頵 | 박**윤** | 박**군** | 드문 한자 오독 |
| 洪霶 | 홍**팽** | 홍**방** | 드문 한자 오독 |
| 傳于兪榥曰 | "전교하기를…" | **유황에게** 전교하기를 | 이름 누락 |

### 5.2 무엇이 번역 품질을 움직이는가 — 프롬프트 6변형 통제 실험

입력 토큰의 85%가 문장이 아니라 고정 프롬프트였다. 60문장 × 3라운드 × 6변형(1,080회 호출)으로 측정했다.

| 변형 | 바꾼 것 | chrF (Δ) | ETS | 토큰 |
|---|---|---|---|---|
| v0 | 기존 생산 프롬프트 (대조군) | 37.90 | 97.1% | 917.9 |
| v1 | 역할·번역 원칙 제거 | 36.42 (−1.48) | = | −12.2% |
| v2 | 문체 변환표 제거 | 37.99 (+0.09) | = | **−13.6%** |
| v3 | 연구의 대표 예시 5개로 교체 | 39.72 (+1.82) | 98.1% | +14.6% |
| **v4 (채택)** | **최소 구성** (정답 표기 예시 5개만) | **40.32 (+2.42)** | **98.1%** | **−11.2%** |
| v5 | 기존 예시의 따옴표·띄어쓰기만 교정 | 39.82 (+1.92) | = | −0.5% |

> - 품질을 움직인 것은 지시문이 아니라 **예시가 정답 코퍼스와 같은 표기로 쓰였느냐**였다.
> - 문체 변환표는 호출당 125토큰을 쓰면서 품질에는 기여하지 않았다.
> - 어느 변형도 ETS를 떨어뜨리지 않았다 — **인명을 지키는 것은 프롬프트 문구가 아니라 KB 주입**이다.
>
> **의사결정.** 사전 등록 규칙("통과 변형 중 토큰 최소")은 v2를 골랐다. 하지만 v4는 토큰이 22개 많을 뿐 품질 지표 3개가 모두 올랐다. 규칙을 사후에 고치지 않고 **규칙의 답(v2)과 실제 채택(v4)을 판정 기록에 나란히 남긴 뒤** v4를 채택했고, 규칙 개정은 다음 실험 전에 한다.

### 5.3 NER 경량화

| 엔진 | p50 | p95 | 모델 크기 | 원본과 완전 일치 | 인명 재현율 |
|---|---|---|---|---|---|
| PyTorch (기준) | 17.9ms | 68.7ms | 709MB | — | 100% |
| ONNX fp32 | 10.6ms | 65.4ms | 709MB | 100% | 100% |
| **ONNX INT8 (채택)** | **8.3ms** | **62.4ms** | **178MB** | 97% | **100%** |

> 문장 단위 완전 일치는 97%로 떨어졌지만, 파이프라인이 실제로 쓰는 신호(인명 검출)의 재현율은 100% 그대로였다. 속도 2.2배, 메모리 1/4.

### 5.4 품질을 깎는 최적화는 증거가 있어야 켠다 — L2 템플릿 캐시

정형문(`以◯爲承旨` 등)의 번역 틀에 **인명만 바꿔 끼우는** 캐시를, 같은 문장의 LLM 번역과 비교했다(1,220쌍).

| 지표 | 임계 | 실측 중앙값 | 판정 |
|---|---|---|---|
| chrF 차이 | −2.0 이내 | −1.28 / +0.04 | ✅ 통과 |
| 확정 인명 재현율 | 하락 0 | 6라운드 전부 1.0000 | ✅ 통과 |

> **품질은 통과했지만 기본 off로 결정했다.** 줄이는 LLM 호출이 +1.74%p(완역 5.72년 → 5.63년)인 반면, LLM이 쓰지 않은 문장 1,392건이 서빙되고 새 장애 지점이 생긴다. 게이트는 켤 **자격**을 판정할 뿐이고, 켤지는 **수혜의 크기**로 정했다.

### 5.5 서빙 성능과 비용

| 항목 | 실측 |
|---|---|
| E2E 지연 중 LLM 비중 | **p95의 99.7~99.9%** |
| 캐시 히트 vs 미스 | **0~12ms** vs 1,665ms (히트 시 LLM·NER 호출 0회) |
| 배치 처리량 | **23 jobs/min** (워커 1대 23.4, 2대 23.1) |
| 강제 종료(kill -9) 후 재개 | 12/12 완료, **job당 LLM 호출 최대 1회** |
| 429 폭주 시 적응형 속도 조절 | 가짜 provider로 유발 — 429 2건에 39→19 RPM으로 감속 후 완주 |

| 시나리오 (남은 1억 5천만 자) | 비용 | 소요 |
|---|---|---|
| 유료 Flash, 캐시 없음 | $803 ≈ 112만 원 | 0.9일 |
| **유료 Flash, 실측 캐시 17.4% 반영** | **$663 ≈ 93만 원** | **0.7일** |
| 무료 티어 (하루 500회) | 0원 | 5.7년 |

> 무료 운영에서는 비용이 아니라 **모델별 일일 한도가 완역 시간을 지배**한다. 남은 레버는 "싸게"가 아니라 "여러 모델의 quota를 모아 쓰기"다. 계산 모델: [`docs/cost-model.md`](docs/cost-model.md)

### 5.6 사용자 관점의 효과

- **검수 부담 감소** — 사람이 가장 놓치기 쉬운 오류(자연스러운 문장 속 틀린 이름)를 2/3 줄였다.
- **판단 근거 제공** — 모든 응답에 VERIFIED / DEGRADED / REJECTED 등급을 붙여, 사전에 없는 인물이 섞인 문장을 검수자가 먼저 볼 수 있다.
- **운영비 0원 공개 경로** — 사용자가 자기 Gemini 키를 헤더(`X-Llm-Key`)로 보내면 그 요청만 그 키로 호출한다. 키는 저장·로깅하지 않는다.

## 6. 트러블슈팅과 한계

### 6.1 트러블슈팅

| 문제 | 원인 | 해결 |
|---|---|---|
| **게이트 오탐률 7배 폭증** (3.9% → 26.6%) | 게이트 버그가 아니라 코퍼스의 원문–번역 정렬 결함(11.24%) | 밀린 짝 검출 규칙 → 제외 후 4.36%로 골든셋과 일치 |
| **429인데 재시도해도 안 풀림** | 같은 429가 분당 한도·일일 한도·**월 지출 상한** 세 가지로 온다. 내장 재시도가 지출 상한 429를 계속 두드렸다 | 응답 본문으로 9종 분류(재시도 / 배치 일시정지 / 즉시 DLQ). 내장 재시도 끄고 분류기가 단독 통제 |
| **실제 429를 재현할 수 없음** | 60 RPM · 워커 2대로도 provider 한도에 닿지 않음 | 실 provider와 같은 오류 본문을 내는 **가짜 LLM provider**를 만들어 quota 0으로 429·503·품질 실패·타임아웃 유발 |
| **job 하나가 26분째 RUNNING** | LLM 호출에 하드 타임아웃이 없었다 | 60초 타임아웃 → TIMEOUT(일시 오류)로 분류해 기존 재시도·서킷 경로에 편입. 로컬 실측: 지연 3초·타임아웃 1초에서 약 6초 만에 FAILED TIMEOUT |
| **동기 API가 429를 500으로 응답** | 실패 분류가 워커에만 있었다 | 분류기를 공용 모듈로 옮겨 API도 같은 규칙으로 429(Retry-After)·503·504·400으로 매핑 |
| **난이도 라우팅이 완역을 7.5배 늦춤** | 상위 모델 수요(29.9%)가 그 quota 몫(3.8%)의 8배 | 난이도 분류와 quota 배정을 분리, 상위 모델은 동명이인 문장(1.8%)에만 |
| **새 모델이 응답 12건 전부 파싱 실패** | JSON 출력 계약을 지키지 않는 모델 | quota 이전에 **출력 형식 계약 준수**를 모델 선택의 첫 관문으로 |
| **인명 품질 99.09%가 순환 지표** | 주입 소스 = 채점 소스 | 독립 정답지 기반 ETS로 교체 |

전체 기록: [`docs/troubleshooting.md`](docs/troubleshooting.md) · 실측 재현 커맨드: [`docs/benchmarks.md`](docs/benchmarks.md)

### 6.2 한계

> **인명 정확도는 97%로 높지만, 코퍼스 전체 인명 멘션의 36.5%가 KB에 없어 실제 활용 범위는 사전 커버리지에 제한된다.**

- **표본 크기** — 통제 실험은 60문장·정답 인명 104명이다. 방향은 라운드 간 변동 0으로 안정적이지만, 효과의 정확한 폭은 표본을 키우면 달라질 수 있다.
- **사전에 없는 인물 문장의 품질 미측정** — 평가셋은 KB가 아는 인물 비중이 높다.
- **정답지 출처 재확인 필요** — 인명 정답지 규모가 선행 연구 보고서 기재값과 달라, 원본 재수집으로 출처를 확정해야 ETS의 독립성을 완전히 보증할 수 있다.
- **chrF의 한계** — 단일 전문가 번역과의 표면 유사도라 사람이 판정한 번역 품질과 다르다.
- **무료 quota** — 운영비 0원 원칙 아래에서는 완역에 5.7년이 걸린다.
- **공개 배포** — 공개 모드 하드닝(API 키 필수, 캐시 미스는 BYOK 필수, 키 마스킹, 하드 타임아웃)과 쿠버네티스 매니페스트는 완료했고, 실습 클러스터 배포는 진행 중이다.

### 6.3 다음 단계

1. **KB 확장** — 등장 빈도 상위 표면형부터(10회 이상만으로 MISS의 42% 해소). 남은 인명 오류를 줄이는 가장 직접적인 레버다.
2. **KB MISS 문장군 품질 측정** — 층화 표본으로 사전에 없는 인물 문장의 ETS를 따로 잰다.
3. **예산 서킷브레이커** — 예산 소진율 70/85/100%에 따라 상위 모델 차단 → 캐시 우선 → 신규 거부로 단계적 저하.
4. **정답지 출처 확정 → NER 재평가** — 사람이 붙인 라벨로 정밀도·재현율을 다시 잰다. 격차가 확인될 때만 NER 재학습을 검토한다.

> **설계 원칙.** LLM은 언어를, 사전은 사실을 맡는다. 모든 개선은 명시적 기준 모델 대비로만 주장하고, 기준은 결과를 보기 전에 고정한다. 품질을 깎는 최적화는 비열등 증거가 있어야 켤 자격을 얻고, 켤지는 수혜의 크기로 정한다.

## 실행 방법

```bash
cp .env.example .env                      # GEMINI_API_KEY=<결제 미연동 프로젝트의 키>
cd ner-server && uv sync && uv run python scripts/export_onnx.py && cd ..   # NER 모델 1회 변환
docker compose -f deploy/docker-compose.yml up -d --build                   # 전 스택

curl -s -X POST localhost:8080/api/v1/translations/sync \
  -H 'Content-Type: application/json' -d '{"text":"以金瑬爲承旨","year":1623}'
```

LLM 호출 없이 전 경로를 확인하려면 `GEMINI_MODEL=fake-flash-lite`(가짜 provider)로 띄운다. 공개 모드 리허설은 `SJW_PUBLIC_MODE=true` — 이때는 `X-Api-Key`(발급: `deploy/k8s/issue-key.sh`)와 `X-Llm-Key`(본인 Gemini 키)가 필요하다.
